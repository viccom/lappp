# F4 · 人物关系档案（家庭档案 → 图片理解的上下文）初步设计

> 状态：草案 v0（2026-11-23）· 分支 `develop` · 前置：F1（图片理解）与 [`VL-提示词模板库.md`](VL-提示词模板库.md) 的结论。
> 本文是**初步设计**：定方向、数据模型、注入方式、隐私边界和分期。逐步的实施计划等方向确认后另出。
> 文中的人一律用角色称呼，不写真实姓名。行号以 2026-11-23 的 `develop` 为准，只作定位线索。

## 0. 一页结论

**要做的东西**：让用户把人脸标注认出的人按家庭角色组织成一份「家庭档案」——根是家庭名称，成员挂在角色和人脸姓名上，带性别、出生年月等属性。图片理解时，把**这张照片里认出的人**的档案作为事实交给模型。

**它不是「训练一个模型」。** 档案是一小段结构化事实（通常 4–8 行），在发请求时拼进提示词。不改模型、不训练、换模型照样有效，改一个字段下一次调用立即生效。

**我的判断：值得做，而且比继续调提示词更值钱。** 今天的数据是它的证据：模板要求「名字对不上就别用」，模型不知道一个名字是谁、几岁、和谁是一家人，于是大部分描述不写人名，还会把没具名的大人写成「先生」。§8 的对照实验（6 个模板 × 6 张照片 × 各 2 轮）里，给模型一张档案卡之后：

- 用上人名或角色词的描述从 19/36、18/36 升到 **33/36、32/36**（89%–92%）。
- 关于孩子的年龄表述：对照组两轮提到的 4 次**全部不对**（还把一次写成「六七岁」），实验组 **15 次全部正确**。
- 把人名或角色安错的人：**0 处**（71 条有效描述逐条核对）。
- 把陌生人或档案外的人说成家人：**0 处**（对照组出现过 2 次「丈夫」）。
- 截断从 0 升到 2/72，这一项需要产品化时盯住。

**四个关键决策**（理由见对应章节）：

| # | 决策 | 为什么 |
|---|---|---|
| D1 | 成员按**人脸标注的名字**关联，不按 `persons.id` | 每次重建人脸索引，`persons` 表都会清空重建，只有名字会被找回来。挂在 id 上的数据会丢。 |
| D2 | 只把**本张照片里认出的人**的档案送进提示词；出生日期只以「拍摄时年龄」送出，成年人年龄默认不送；出生地、备注默认只存不发 | 少发就少错、少泄露。请求会经网关发往云端模型。 |
| D3 | 档案存图库自己的 SQLite（迁移 v33 新表），适用范围按相册 | `LibraryState` 是前端整包覆盖写的，放进去会被冲掉。相册是现成的顶层分类。 |
| D4 | 内置模板文本改动时播种**新版本行**，不原地改 | 模板行按设计不可变；定时任务和已有标注都引用模板 id。 |

**明确不做**（至少第一版）：微调或训练模型；自动推断人物关系并当作事实；家庭树编辑器；把人脸裁切图发给模型；档案云同步。

## 1. 问题、目标与指标

### 1.1 现状的三个缺口

今天的实测（见 `VL-提示词模板库.md` §7）：

1. **模型不知道名字背后是谁。** 一个名字只是几个字，不是「9 岁的儿子」。按画面位置排序后，三轮 198 条描述里只有 53 条用了人名。
2. **模型不知道谁和谁是一家人。** 一张有陌生男子的合影上，角色模板两次把他写成丈夫。
3. **模型不知道年龄。** 同一个孩子在不同年份的照片里岁数不同，模型只能凭长相猜：对照组 4 次关于他的年龄表述全部猜错（把 8 岁写成「六七岁」），之后就干脆绕开不写。

### 1.2 目标

- 用户能在界面里建一份家庭档案：家庭名称、成员（角色 + 人脸姓名 + 属性）、适用的相册。
- 有档案的照片，描述里用对的称呼、角色和年龄；没有档案的照片，行为与现在**完全一致**。
- 档案只对适用范围内的照片生效。
- 用户能看到「模型将看到什么」。

### 1.3 非目标

- 不改变人脸识别本身（聚类、合并、拆分都不在范围内）。
- 不让模型推断关系：档案里没有的关系一律不写。
- 不把档案写回照片文件或 XMP。
- 第一版不做「自动建议角色」。

### 1.4 成功指标

在 6 张基准照片上，每个配置至少跑两轮（纪律见 `VL-提示词模板库.md` §5.3）。最后一列是 §8 那次档案卡实验的结果——它验证的是「档案有用」，不是产品的最终数值。

| 指标 | 现状 | 目标 | §8 实测（2 轮） |
|---|---|---|---|
| 认出家庭成员的照片上，描述用了人名或角色词 | 18–19 / 36（50%–53%；只算人名是 7 和 12） | ≥ 85% | 32–33 / 36（89%–92%） |
| 把人名或角色安给错的人 | 0（今天已修） | 0 | 0 / 71 |
| 把没具名的人说成家人 | 72 条角色输出里 2 条 | 0 | 0 / 71 |
| 关于孩子的年龄表述正确 | 0 / 4 | 100% | 15 / 15 |
| 写出档案里没有的属性 | — | 0 | 0 |
| 时段错误 | 0 / 176 | 不高于现状 | 0 / 72 |
| 截断 | 0 / 176 | 不高于现状 | 2 / 72（略升，§10 盯住） |
| 没有档案的用户，提示词与现在 | — | 逐字节一致（测试） | 未测（机械保证，见 §7.4） |

## 2. 概念与方案比较

### 2.1 「模型」这个词

你描述的东西在机器学习里叫「上下文注入」或「知识卡」，不叫模型。建议界面上叫**「家庭档案」**，代码里叫 `household`，避免让人以为要训练什么。

### 2.2 四种做法

| 做法 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A | 档案作为事实拼进提示词 | 立即生效、可随时改、与模型无关；档案很小（几十个成员以内）不需要检索 | 占用少量 token；档案错了描述就跟着错 | **采用** |
| B | 用家庭照片微调或训练 | 不用每次带上下文 | 网关的模型不是我们能训练的；年龄每年变；没有照片就无法学会名字对应谁 | 不做 |
| C | 本地向量库检索人物资料再拼提示词 | 能装很多资料 | 家庭档案总共几行，检索是多余的复杂度 | 不做 |
| D | 让模型从照片推断谁是谁的什么人 | 用户不用录入 | 准确率不可控，猜错的关系会被当成事实写进描述 | 只允许「建议 + 用户确认」，第一版不做 |

### 2.3 别人怎么做的

- **同类产品**：Immich 和 PhotoPrism 都把人脸聚成人物、让用户命名，Immich 还能合并和隐藏人物。从它们的文档看，都停在「这个人是谁」，没有人物之间的关系（检索所见，没有逐个功能核实）。
  - <https://docs.immich.app/features/facial-recognition>
  - <https://docs.photoprism.app/user-guide/organize/people/>
- **研究**：个性化视觉语言模型的方向上，已有工作用知识图谱表达用户特有概念之间的关系，并训练模型据此推理（ReGraP-LLaVA）；MyVLM 让模型学会「这是谁」。思路一致——结构化的个人知识加推理——但它们靠训练，我们靠上下文。
  - <https://arxiv.org/abs/2505.03654>
  - <https://arxiv.org/abs/2403.14599>
- **隐私惯例**：Google 对儿童的受监督账号关闭人脸分组。涉及未成年人的信息应当比成年人的更保守。
  - <https://support.google.com/families/answer/7103261>

## 4. 领域模型

```
家庭档案 Household
├─ 名称            「我家」
├─ 用于图片理解     开 / 关
├─ 适用相册        [家庭相册]  （不选 = 整个图库）
└─ 成员 Member（第一层）
   ├─ 人脸姓名      必须与人脸标注里的名字一致
   ├─ 称呼          描述里怎么叫；空则用人脸姓名
   ├─ 角色          儿子 / 女儿 / 父亲 / 母亲 / 爷爷 / 奶奶 / 外公 / 外婆 /
   │                兄弟姐妹 / 其他亲属 / 朋友 / 同事 / 同学 / 其他
   ├─ 性别          男 / 女 / 未知
   ├─ 出生年月      可只填年份
   ├─ 出生地        可选
   ├─ 备注          可选
   └─ 两个开关       年龄是否告诉模型；出生地与备注是否告诉模型
```

**角色是相对「家里的孩子」说的。** 儿子和女儿是参照点；「外婆」指孩子的外婆，「父亲」指孩子的父亲。没有孩子成员的档案，角色只按字面用（「成员 X，父亲」）。

**成员与人脸的关联靠名字。** 人脸标注里的名字等于成员的「人脸姓名」，就算认出。两个 `persons` 行同名时自动合并看待——这正是现在没有合并功能时用户已经在用的办法。

**改名要跟着走。** 用户给人脸改名时，同步更新档案里相同的旧名字（`rename_with_conn`，`t_sqlite.rs:10639` 附近，一条 `UPDATE`）。

### 4.1 数据模型（迁移 v33）

```sql
CREATE TABLE IF NOT EXISTS households (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL,
    enabled     INTEGER NOT NULL DEFAULT 1,   -- 用于图片理解
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS household_members (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    household_id  INTEGER NOT NULL REFERENCES households(id) ON DELETE CASCADE,
    person_name   TEXT NOT NULL,               -- 人脸标注里的名字，不是 persons.id
    display_name  TEXT,
    role          TEXT NOT NULL,
    role_label    TEXT,                        -- 自定义称呼
    gender        TEXT NOT NULL DEFAULT 'unknown',
    birth_date    TEXT,                        -- 'YYYY' | 'YYYY-MM' | 'YYYY-MM-DD'
    birth_place   TEXT,
    notes         TEXT,
    share_age     INTEGER NOT NULL DEFAULT 1,
    share_details INTEGER NOT NULL DEFAULT 0,
    created_at    INTEGER NOT NULL,
    updated_at    INTEGER NOT NULL,
    UNIQUE (household_id, person_name)
);

CREATE TABLE IF NOT EXISTS household_albums (
    household_id INTEGER NOT NULL REFERENCES households(id) ON DELETE CASCADE,
    album_id     INTEGER NOT NULL REFERENCES albums(id) ON DELETE CASCADE,
    PRIMARY KEY (household_id, album_id)
);
```

为什么这样设计：

- **没有指向 `persons` 的外键。** 那张表会被清空重建（事实表第 2 行）。
- **一个相册可以被多份档案覆盖。** 渲染时取所有适用档案里匹配到的成员的并集。两家人的照片放在同一个相册里也不会冲突。
- **不建成员之间的关系表。** 第一版靠角色就够写出「孩子的外婆」。真正的关系边留给第二版（§9）。

## 5. 注入提示词

### 5.1 档案卡长什么样

只包含这张照片里认出的人。下面是样张 A（四人公园合影）会得到的卡，名字已换成角色：

```
人物档案（用户整理，可信；只描述画面里已认出的人）：
- 外婆：孩子们的外婆，女
- 母亲：孩子们的母亲，女
- 父亲：孩子们的父亲，男
- 儿子：这个家庭的儿子，男，拍摄时约 10 岁
画面里没有被认出的人身份不确定：不要用上面的名字称呼，也不要断定与这个家庭的关系。
```

规则：

- 照片里没有认出任何成员，就**整卡不发**，提示词与现在逐字节一致。
- 出生年月只填到年 → 「约 N 岁」；填到月 → 「约 N 岁」；填到日 → 「N 岁」。
- 拍摄时不满 18 岁才写年龄；成年人的年龄默认不写（`share_age` 只管未成年人，第二版再细分）。
- 出生地、备注默认不写；用户打开 `share_details` 才追加在行尾。
- 性别只在已知时写。
- 称呼与人脸姓名不同时写成「称呼（人脸姓名）」，模型用称呼。

### 5.2 接进模板

- 新增一个占位符 `{family}`：展开成上面的卡，或者空字符串。占位符表从 36 个变 37 个。
- 取数点在 `prompt_context_with_conn`（`t_vl.rs:1341` 附近，现在已经在这里取标签和人名）：由文件找到相册，找到适用的档案，与人脸姓名求交集。两次小查询，有索引。
- 11 个内置模板的共享事实块加一行 `{family}`。按 D4，这是模板的新版本。
- 共享规则里「不要推断关系」那几条要改口径：有档案时「关系、角色、年龄以人物档案为准，档案里没有的不要推断」；没有档案时保持现在的措辞，所以这两句也要做成随档案出现与否切换的占位符。
- 每次调用实际发送的提示词存在 `vl_calls.prompt_actual`，实验室里能看到那一张卡。档案因此会出现在本地的调用证据里，这是有意的：出了错能查到模型当时看到了什么。

### 5.3 角色模板跟着受益

有了档案，「爸爸的视角」不需要猜谁是爸爸。实验里模型的处理是对的：父亲在画面里就以父亲的身份写，不在画面里就写成「我在镜头后看着」。第一版不专门改角色模板；第二版可以按档案里有没有对应角色的成员来决定是否显示某个角色模板。

## 6. 隐私

**哪些数据会离开这台机器。** 提示词经局域网网关发往上游云端模型。今天人名已经在发（`{people}`）。档案会新增角色、性别、年龄，而且它们与拍摄时间、地点出现在同一个请求里，合起来比单独一项更能识别一个人。未成年人尤其如此。

**因此：**

| 控制 | 默认 |
|---|---|
| 档案总开关「用于图片理解」 | 开；关掉后只存本地 |
| 成年人的年龄 | 不发 |
| 出生日期本身 | 永远不发，只发推算出的年龄 |
| 出生地、备注 | 不发；每个成员单独打开 |
| 发送前的知情提示 | 第一次打开「用于图片理解」时说明会发送哪些字段 |
| 预览 | 编辑器里选一张照片，逐字显示模型将看到的卡 |
| 写回 | 档案只存在图库库里，不写进照片文件、XMP 或任何导出 |

备份图库（`scripts/backup-library-db.py`）会连同档案一起备份，这是对的。

## 8. 对照实验（2026-11-23）

**问的问题**：给模型一张档案卡，描述会不会更像用户想要的？

**做法**：产品内置模板里取 6 个（客观描述、爸爸的视角、妈妈的视角、儿子的视角、家庭合影、亲子时光），6 张基准照片（见 `VL-提示词模板库.md` §5.2）。实验组把一张手写的档案卡插在每个模板的规则之前，跑两轮；对照组是今天同配置、不带卡的两轮。评判脚本和指标在看到结果之前写好。

实验用的卡（名字换成角色；**出生年是假设值，未经用户确认**）：

```
人物档案（用户整理的家庭关系，可信；只用于画面里已被人脸标注认出的人。
没被认出的人不要按档案里的人称呼，也不要当成这个家庭的成员）：
- 儿子：这个家庭的儿子，男，2011 年生（年龄请按拍摄时间推算）。
- 父亲：父亲，男，儿子的父亲。
- 母亲：母亲，女，儿子的母亲。
- 外婆：儿子的外祖母（外婆），母亲的母亲。
```

卡片里没有另两个孩子（样张 C 的女孩、样张 F 的另一个孩子），正好用来检验模型会不会把档案外的人说成家人。

**结果**

对照组 A、B 是今天不带卡的两轮（「提交配置终验」和「原图终验」，同一批模板与照片）；实验组带卡跑两轮。每轮 36 条。

| 指标（每轮 36 条） | 对照组 A | 对照组 B | 实验组第 1 轮 | 实验组第 2 轮 |
|---|---|---|---|---|
| 用了人名 | 7 | 12 | 28 | 26 |
| 用了人名或角色词 | 19 | 18 | 33 | 32 |
| 写明了关系（X 的母亲…） | 4 | 6 | 12 | 10 |
| 关于儿子的年龄表述，与假设的出生年一致 | 0 / 1 | 0 / 3 | 6 / 6 | 9 / 9 |
| 没有拿到可用回答（额度用尽） | 0 | 0 | 1 | 0 |
| 时段写错 | 0 | 0 | 0 | 0 |
| 把档案外的人说成家人 | 0 | 0 | 0 | 0 |
| 描述字数（中位数） | 110 | 109 | 106 | 111 |
| 输出 token（每轮合计） | 53,159 | 57,829 | 55,129 | 50,287 |
| 单次耗时（均值） | 10 秒 | 11 秒 | 26 秒 | 13 秒 |

逐条人工核对两轮的 71 条有效描述（第 1 轮 35 条、第 2 轮 36 条）：

- **人名和角色全部安对，0 处安错。** 之前反复出错的父子合影，这次「妈妈的视角」写的是「维康戴眼镜穿深色上衣，开源穿浅绿 T 恤」。
- **陌生人不被说成家人。** 有未具名男子的样张 E 上，两轮共 12 条都写成「男士」「一位大人」「旁边的男士」；对照组那 2 条「丈夫」没有再出现。
- **档案外的人不被说成家人。** 另两个孩子只以名字或「一位别着粉色发夹的小姑娘」「旁边几个孩子」出现。
- **没有编造档案里没有的属性**（职业、出生地都没有出现）。
- **年龄全部算对。** 2021 年的照片写「十岁」，2020 年 5 月写「9 岁」，2020 年 2 月写「八九岁」，2019 年 4 月写「七八岁」「八岁」，与假设的出生年 2011 一致。对照组同样的照片写「六七岁」（错），而且一遇年龄就绕开不写（对照组两轮只有 4 次年龄表述）。
- **角色模板的口吻对了**：父亲不在画面里时写成「我在镜头后看着你们」，没有把自己塞进画面；母亲在画面里时用「我」指自己，用「我妈」指外婆。
- **一处小的位置错误**（第 1 轮）：「父母一左一右靠近儿子」，实际两人都站在儿子左边。第 2 轮同一张写对了。

**代价与没弄清的事**

- **截断略高**：实验组两轮各有 1 次输出触到 4000 的额度（第 2 轮那次仍拿到了正文），对照组 72 次里 0 次。样本太小，不能确定是档案卡让思考变长，还是那两张照片本来就难。**产品化时要盯住这个指标**（§10）。
- **耗时不能归因**：第 1 轮均值 26 秒、第 2 轮 13 秒，对照组两轮是 10 秒和 11 秒；而每轮输出的 token 总量相当（5.0–5.5 万）。第 1 轮很可能是网关当时的负载。**没有证据表明档案卡让请求变重。**
- **实验用的是静态卡**，产品里会按照片动态生成（只列认出的人）；两者在这一步上等价，但产品里年龄由程序算好，不再让模型推算。
- **卡里的关系是我的推断**，错了模型会照着错。产品里必须让用户自己填。
- **只覆盖 6 张照片、6 个模板、2 轮**。其中只有 2 张（C、F）含档案外的人，用来测「不越界」，数量偏少。

- 人物外观小传：从人脸封面生成「戴眼镜、短发」之类的辨认线索（会发送人脸裁切图，默认关闭）。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 档案填错，描述跟着错得很自信 | 预览逐字可见；每张标注都存了当时的提示词，可追溯 |
| 没被认出来的家人被当成陌生人 | 这是更安全的一侧错误。规则写的是「身份不确定」，不是「不是家人」 |
| 未成年人信息离开设备 | 年龄只发推算值；总开关；知情提示；成年人默认不发 |
| 模型过度使用档案，把只认出一人的照片也写成「一家人」 | 卡片只列在场的人；评估里把「档案外的人被说成家人」作为硬指标 |
| 上游同步冲突 | 新代码全在新文件；`t_vl.rs`、`t_sqlite.rs`、`Settings.vue` 各只加几行，位置记在 §7.3 |
| 带卡之后截断变多 | 评估里盯住截断率；必要时把卡的措辞压短，或再调额度 |
| 人脸重建索引后名字变了 | 改名时同步；评估里加一条「改名后档案仍然匹配」 |

## 11. 需要你定的事

1. **一个图库建几份档案？** 我按「可以多份、相册可以重叠」设计。你家如果只有一份，界面可以更简单。
2. **年龄的默认值。** 我定的是「未成年人发年龄，成年人默认不发」。可以改成全部不发或全部发。
3. **角色相对「家里的孩子」来说**，可以吗？没有孩子的家庭（只有夫妻）角色只按字面用。

5. **实验里我假设的出生年和推断的关系**（谁是母亲、谁是外婆）请纠正一下；做基准要用正确的值。

## 12. 顺带发现的现有问题

都不是这个功能引入的，但和它相关：

1. **`Person N` 会进提示词和搜索索引。** 今天的提示词里出现过「Person 111, 〈名字〉, 〈名字〉」这样的列表。
