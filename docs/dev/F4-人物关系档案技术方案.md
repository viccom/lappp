# F4 · 人物关系图谱（家庭档案 → 图片理解的上下文）初步设计

> 状态：草案 v0（2026-11-23）· 分支 `develop` · 前置：F1（图片理解）与 [`VL-提示词模板库.md`](VL-提示词模板库.md) 的结论。
> 本文是**初步设计**：定方向、数据模型、注入方式、隐私边界和分期。逐步的实施计划等方向确认后另出。
> 文中的姓名一律是化名（张伟 / 李静 / 张小满 / 王秀兰 等），不是真实姓名。行号以 2026-11-23 的 `develop` 为准，只作定位线索。

## 0. 一页结论

**要做的东西**：一个**独立的模块**——对象是人（从人脸标注导入），Link 是关系（父母、配偶、同学、师生），属性（性别、出生年月）挂在对象上。图片理解时，把**这张照片里认出的人**连同他们之间的关系，投影成一小段事实交给模型。

**不配置就等于不存在。** 表按需创建：没建图谱的图库连表都没有，VL 侧查一次 `sqlite_master` 就跳过，提示词与现在逐字节相同。删掉这个模块等于没这功能（D5）。

**它不是「训练一个模型」。** 图谱是数据：通常几十个节点、几十条边。每次发请求时投影成 4–8 行文字拼进提示词。不训练、不改模型、换模型照样有效；改一条边，下一次调用就生效。

**我的判断：值得做，而且比继续调提示词更值钱。** 今天的数据是它的证据：模板要求「名字对不上就别用」，模型不知道一个名字是谁、几岁、和谁是一家人，于是大部分描述不写人名，还会把没具名的大人写成「先生」。

§8 做了两轮对照（6 个模板 × 6 张照片 × 各 2 轮，共 144 次调用）——先验「角色列表卡」，再按你的澄清验「图谱卡」：

| | 不带卡（对照） | 图谱卡 |
|---|---|---|
| 用上人名或角色词 | 19/36、18/36 | **32/36、29/36** |
| 关于孩子的年龄表述正确 | 0/4 | **7/7、7/7** |
| 给人名或角色安错人 | 0 | **0**（144 条逐条核对） |
| 给图谱外的人编关系（妹妹/表姐…） | — | **0**（72 条 0 处） |
| 把陌生人或图谱外的人说成家人 | 出现过 2 次「丈夫」 | **0** |
| 截断 | 0/72 | 1/72（需产品化时盯住） |

图谱卡与角色列表卡的质量没有可辨差异；选图谱是因为**数据模型更强**——输入更少、不会自相矛盾、换参照点不用改数据。有一个具体差别：图谱卡能让「妈妈的视角」写出「我站在**我妈**和张伟中间」，因为「外婆是李静的母亲」这条边是推导出来的，而角色列表卡只给了一个「外婆」的词。

**它解决的是「身份与关系」，不是「画面细节与事件」。** 身份、关系、年龄、时间补上之后，实测安错人 0、编关系 0、年龄全对；但空间站位、细节真伪、角色口吻、事件因果仍会出错（§8.4 列了实测到的例子）。再往上推靠三件事，已排进 §9：**人脸裁切图 + 名字**（让名字与脸绑定变明确）、**结构化输出**（给「不确定」留位置）、**同事件多图**（写得出事件而不只是一帧）。

**十个关键决策**（理由见对应章节）：

| # | 决策 | 为什么 |
|---|---|---|
| D0 | **关系用图谱存**：亲属只存 `parent` 与 `spouse` 两种边，其余（父系母系的祖辈、兄弟姐妹长幼、舅姨伯叔姑、儿媳女婿、姻亲、堂表）由遍历推导；社交关系单列 `social` 边；**不存「角色」字段** | 输入最少（4 个家人 4 条边）、不会自相矛盾、加一个人自动补全所有关系。同学/师生推不出来，所以必须有自己的边类型（§4.2） |
| D1 | 对象有**稳定的 id**；人脸标注的名字只是**锚点**（一个对象可以有多个脸名，也可以没有），不按 `persons.id` | 每次重建人脸索引，`persons` 表都会清空重建，只有名字会被找回来，挂在 id 上的数据会丢；而一个人也不等于一个脸名（§4.5） |
| D2 | 只把**本张照片里认出的人**、以及**在场两人之间**的关系送进提示词；出生日期只以「拍摄时年龄」送出，成年人年龄默认不送；出生地、备注默认只存不发 | 少发就少错、少泄露。请求会经网关发往云端模型。 |
| D3 | 图谱存**图库自己的 SQLite**（六张表，按需创建，见 D5），适用范围按相册 | `LibraryState` 是前端整包覆盖写的，放进去会被冲掉；每库一份也符合「模块可不存在」。相册是现成的顶层分类。 |
| D4 | 内置模板文本改动时播种**新版本行**，不原地改 | 模板行按设计不可变；定时任务和已有标注都引用模板 id。 |
| D5 | **做成独立模块，不配置就等于不存在**：表按需创建（不进迁移链），VL 侧先查一次 `sqlite_master` 就跳过 | 用户不建图谱，库里连表都没有；删掉模块等于没这功能；少改迁移清单与 10 处版本断言（§4.3） |
| D6 | **建图靠导入，展示靠融合**：人名从人脸标注导入，用户再连父母/配偶/社交三种边；关系显示在人物侧栏与信息面板里，不另开大页面 | 用户已经命名过人脸，不该再录一遍；关系属于人物，应该在人物出现的地方看到（§7.2） |
| D7 | **根人物必填**：`households.root_node_id`，界面置顶，称呼相对它推导，图谱名默认「〈根〉家」 | 称呼（父亲/儿子/外婆）必须相对某个人才成立；根就是你说的「以谁为家的那个人」（§4.4.1） |
| D8 | **边带有效期**（按年），按**拍摄当时**成立与否写关系 | 照片都有拍摄时间：结婚之前不是「妻子」，离婚之后是「前妻」（§4.8） |
| D9 | **边带来源**；只有用户确认或批量导入的边才进提示词 | 否则 M2 的「建议一条边」会把猜测写成事实（§4.8） |
| D10 | **模式是代码里的封闭目录**：对象类、关系类型、每种关系的约束只有一处定义 | 按需建的表没有版本号，放宽一个 `CHECK` 只能重建表；目录是普通数据，可以穷举测试（§4.6） |

**明确不做**（至少第一版）：微调或训练模型；让模型推断关系并当作事实；图形化家庭树编辑器（M2）；把人脸裁切图发给模型；图谱云同步。

## 1. 问题、目标与指标

### 1.1 现状的三个缺口

今天的实测（见 `VL-提示词模板库.md` §7）：

1. **模型不知道名字背后是谁。** 一个名字只是几个字，不是「9 岁的儿子」。按画面位置排序后，三轮 198 条描述里只有 53 条用了人名。
2. **模型不知道谁和谁是一家人。** 一张有陌生男子的合影上，角色模板两次把他写成丈夫。
3. **模型不知道年龄。** 同一个孩子在不同年份的照片里岁数不同，模型只能凭长相猜：对照组 4 次关于他的年龄表述全部猜错（把 8 岁写成「六七岁」），之后就干脆绕开不写。

### 1.2 目标

- 用户能在界面里画出这份图谱：对象（从人脸标注导入，带性别、出生年月）、Link（父母、配偶、同学、师生，可带起止年份）、适用的相册。
- 有图谱的照片，描述里用对的称呼、关系和年龄；没有图谱的照片，行为与现在**完全一致**。
- 档案只对适用范围内的照片生效。
- 用户能看到「模型将看到什么」。

### 1.3 非目标

- 不改变人脸识别本身（聚类、合并、拆分都不在范围内）。
- 不让模型推断关系：档案里没有的关系一律不写。
- 不把档案写回照片文件或 XMP。
- 第一版不做「自动建议一条边」。

### 1.4 成功指标

在 6 张基准照片上，每个配置至少跑两轮（纪律见 `VL-提示词模板库.md` §5.3）。后两列是 §8 两次实验的结果——它们验证的是「把人物的真实信息交给模型有用」，不是产品的最终数值。

| 指标 | 现状 | 目标 | §8.1 角色列表卡 | §8.2 图谱卡 |
|---|---|---|---|---|
| 认出图谱里人的照片，描述用了人名或角色词 | 18–19 / 36（只算人名是 7 和 12） | ≥ 85% | 32–33 / 36 | 29–32 / 36 |
| 给人名或角色安错人 | 0（今天已修） | 0 | 0 | 0 |
| 给图谱外的人编关系 | — | 0 | 0 | 0 |
| 把没具名的人说成家人 | 72 条角色模板输出里 2 条 | 0 | 0 | 0 |
| 关于孩子的年龄表述正确 | 0 / 4 | 100% | 15 / 15 | 14 / 14 |
| 写出图谱里没有的属性 | — | 0 | 0 | 0 |
| 时段错误 | 0 / 176 | 不高于现状 | 0 / 72 | 0 / 72 |
| 截断 | 0 / 176 | 不高于现状 | 2 / 72 | 1 / 72（§10 盯住） |
| 没有图谱的用户，提示词与现在 | — | 逐字节一致（测试） | 未测（机械保证，见 §7.4） | 同左 |

## 2. 概念与方案比较

### 2.1 名词对齐

你说的「模型」是**关系图谱**（knowledge graph）的意思，不是机器学习里那个「模型」。两者在这个功能里的位置不同：

- **图谱**是数据：节点是人，边是关系，属性挂在节点上。§4 就是它。
- **提示词里的那张卡**是图谱的一次投影：只投影这张照片里认出的人，和这些人之间的关系。§5 讲这个。
- 没有任何训练。换一个网关模型，图谱照样能用；改一条边，下一次调用就生效。

界面和代码里建议叫**「家庭档案」**（代码 `household`），避免让人以为要训练什么。

### 2.2 四种做法

| 做法 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A | 图谱作为事实拼进提示词 | 立即生效、可随时改、与模型无关；图谱很小（几十个人）不需要检索 | 占用少量 token；图谱错了描述就跟着错 | **采用** |
| B | 用家庭照片微调或训练 | 不用每次带上下文 | 网关的模型不是我们能训练的；年龄每年变；没有照片就无法学会名字对应谁 | 不做 |
| C | 本地向量库检索人物资料再拼提示词 | 能装很多资料 | 家庭图谱总共几十个节点，检索是多余的复杂度 | 不做 |
| D | 让模型从照片推断谁是谁的什么人 | 用户不用录入 | 准确率不可控，猜错的关系会被当成事实写进描述 | 只允许「建议 + 用户确认」，第一版不做 |

### 2.3 别人怎么做的

- **同类产品**：Immich 和 PhotoPrism 都把人脸聚成人物、让用户命名，Immich 还能合并和隐藏人物。从它们的文档看，都停在「这个人是谁」，没有人物之间的关系（检索所见，没有逐个功能核实）。
  - <https://docs.immich.app/features/facial-recognition>
  - <https://docs.photoprism.app/user-guide/organize/people/>
- **研究**：个性化视觉语言模型的方向上，已有工作用知识图谱表达用户特有概念之间的关系，并训练模型据此推理（ReGraP-LLaVA）；MyVLM 让模型学会「这是谁」。思路一致——结构化的个人知识加推理——但它们靠训练，我们靠上下文。
  - <https://arxiv.org/abs/2505.03654>
  - <https://arxiv.org/abs/2403.14599>
- **隐私惯例**：Google 对儿童的受监督账号关闭人脸分组。涉及未成年人的信息应当比成年人的更保守。
  - <https://support.google.com/families/answer/7103261>

## 4. 领域模型：关系图谱

一份家庭本体就是一张小图谱：**对象是节点，Link 是边**。属性挂在节点上，关系挂在边上。

```
        王秀兰
           │ parent
           ▼
        李静 ──spouse── 张伟
           │ parent        │ parent
           └──────┬────────┘
                  ▼
               张小满
```

严格说它有三层，不要混在一起：

| 层 | 内容 | 落在哪里 |
|---|---|---|
| **实例层** | 对象实例（张伟、李静）和它们之间的 Link——这才是「图」 | 图库里按需建的几张表 |
| **模式层** | 有哪几类对象、哪几类 Link，以及**每种 Link 的约束**（能连哪些类、方向、对称还是互逆、能否推导、是否有时效）——这才是「本体」 | 代码里的封闭目录（§4.6） |
| **投影** | 从整张图里取哪一部分交给 VL | 图谱卡（§5） |

**家庭本体的价值不在「是图」，而在边上的约束。** 社交网络、知识图谱、家谱都是「节点 + 边」，区别全在约束上。

### 4.1 对象与 Link

**对象**（节点）——第一版只有「人」这一类：

| 字段 | 说明 |
|---|---|
| 稳定 id | 对象的身份。图库里唯一，不随人脸重建、改名而变（§4.5） |
| 对象类 | 第一版只有 `person`；`place`、`event` 留给后续（§4.7） |
| 脸名锚点 | 零个或多个。把对象对应到人脸标注里的名字（§4.5） |
| 称呼 | 可选。默认用脸名。用户想让孩子记「妈妈」而不是名字时填 |
| 性别 | 男 / 女 / 未知。推导关系词要用（父亲还是母亲、哥哥还是姐姐） |
| 出生日期 | 可只填年。用来算拍摄时的年龄，也用来区分长幼（哥哥还是弟弟、伯伯还是叔叔） |
| 出生地 | 可选，默认不发送 |
| 备注 | 可选，默认不发送 |
| 两个开关 | 年龄是否告诉模型；出生地与备注是否告诉模型 |

**Link**（边）有几种，性质各不相同：

| Link | 方向 | 存哪一侧 | 参与亲属推导 | 可带有效期 | 例子 |
|---|---|---|---|---|---|
| `parent` | 有向：父母 → 子女 | 只存父母 → 子女 | 是 | 否 | 李静 → 张小满 |
| `spouse` | 无向 | 只存一条（id 小的节点在前） | 是 | 是 | 李静 ── 张伟 |
| `social`·`classmate` / `friend` / `colleague` / `neighbour` | 无向 | 同上 | **否** | 是 | 张小满 ── 同学 ── 陈小雨 |
| `social`·`teacher` | 有向：老师 → 学生 | 只存老师 → 学生；「学生」是它的逆，不单独存 | **否** | 是 | 刘洋 → 张小满 |

`social` 的 `label` 只允许一个封闭小集合：`classmate`（同学）、`teacher`（老师，反向读作「学生」）、`friend`（朋友）、`colleague`（同事）、`neighbour`（邻居）。**它不参与亲属推导**——否则「同学的父亲」会被算成亲戚；但它会进提示词（「张小满和陈小雨是同学」），这样模型不会把同龄孩子写成「妹妹」。

每条边还带两样与「谁和谁是什么关系」无关、但决定这条边能不能用的信息：

| 字段 | 说明 |
|---|---|
| **有效期** `valid_from` / `valid_to` | 按年，可空；空表示不限。很多关系只在一段时间里成立（§4.8） |
| **来源** `source` | `user`（用户确认）/ `imported`（批量导入）/ `suggested`（建议，未确认）。只有前两种算事实（§4.8） |

**没有「角色」字段。** 第一版草案把人压平成「角色 + 属性」，那是我理解偏了：角色的含义取决于参照点（「儿子」相对于谁？），而且一旦有第二个孩子、两边老人、重组家庭，一个字段就装不下。图谱不存角色，**角色是算出来的**（§4.4 与 §4.4.1 的根）。

### 4.2 为什么只存这三种边

| 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 全量存关系边（父、母、兄、弟、配偶、舅、姨、堂、表、儿媳、女婿…） | 每条边都是显式的 | 用户要输 N² 条；同一个人可以同时被标成「表姐」和「姐姐」，图谱自相矛盾；新增一个人要让所有人重新连线 | 不做 |
| **只存 `parent` + `spouse`，亲属关系全部推导；社交关系单列 `social`** | 输入最少（四个家人四条边）；加一个成员自动补全所有关系；亲属部分不可能自相矛盾 | 推导表要覆盖到多深；推不出的关系只能不写 | **采用** |
| 只存「角色」字段 | 输入更少 | 见 §4.1；无法表达两两关系，也定不了参照点 | 不做 |

为什么「同学、师生」必须单独列一种边：**它们不是亲属关系，无论怎么组合父母与配偶都推不出来**。把它们塞进 `parent`/`spouse` 会污染推导，所以只能给它们自己的边类型和封闭标签集（§4.1）。这一类关系也只允许这几个标签，不做无边界的自由文本——放开就等于让用户写一段话进提示词，得不偿失。

推导是纯函数，可以穷举测试。历史数据里同一张照片常有四五个人，图谱一次输入、之后每张照片都受益。

### 4.3 表的建法：按需创建，不进迁移链

既然这个模块**不配置就等于不存在**，表也不该预先建好。第一次创建图谱时由模块自己建：

```rust
// t_household.rs，只在第一次写入前调用
pub(crate) fn ensure_schema(conn: &Connection) -> Result<(), String> {
    conn.execute_batch(
        "<六张表的 CREATE TABLE，见下>",
    )
}
```

对「不存在」的判断只有一个廉价查询：`sqlite_master` 里有没有 `household_nodes`（`t_vl.rs` 已有 `table_exists`）。没有就整段跳过，提示词一个字节都不变。

**为什么不像其它功能那样走迁移链**

| | 写进迁移（v33） | 按需创建（采用） |
|---|---|---|
| 不用的图库 | 六张空表永远存在 | 什么都没有 |
| 模块独立性 | 表是全局 schema 的一部分，删模块要留迁移 | 删模块 = 删文件，旧表留着也无人读 |
| 改动面 | `t_migration.rs` + 测试里 10 处硬编码版本号 + `AGENTS.md` | 只在新模块里 |
| 跨库读取 | 非当前图库不会自动升级迁移，要容忍「表不存在」和「表存在但空」两种情形 | 只有一种情形要处理：表不存在 |
| 代价 | — | 表结构没有版本号，将来改列要自己写「加列」逻辑（`table_has_column` 已有） |

如果更偏好仓库现有的迁移约定，改成 v33 也只是把 `ensure_schema` 的 SQL 搬进 `get_migrations()`；其它设计不变。这一点列进 §11 让你拍。

**表结构**

```sql
-- 对象（节点）。图库级：一个人只有一个对象，不属于某一份图谱。
CREATE TABLE IF NOT EXISTS household_nodes (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    kind          TEXT NOT NULL DEFAULT 'person',   -- 取值由代码目录约束（§4.6）
    display_name  TEXT,                            -- 称呼，可选
    gender        TEXT NOT NULL DEFAULT 'unknown', -- male / female / unknown
    birth_date    TEXT,                            -- 'YYYY' | 'YYYY-MM' | 'YYYY-MM-DD'
    birth_place   TEXT,
    notes         TEXT,
    share_age     INTEGER NOT NULL DEFAULT 1,
    share_details INTEGER NOT NULL DEFAULT 0,
    created_at    INTEGER NOT NULL,
    updated_at    INTEGER NOT NULL
);

-- 锚点：把对象对应到人脸标注里的名字。一个对象可以有多个，也可以没有。
CREATE TABLE IF NOT EXISTS household_node_anchors (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    node_id    INTEGER NOT NULL REFERENCES household_nodes(id) ON DELETE CASCADE,
    kind       TEXT NOT NULL,                      -- 取值由代码目录约束；第一版只有 face_name
    value      TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    UNIQUE (kind, value)                           -- 一个脸名在图库里只对应一个对象
);

-- 图谱：根 + 成员 + 适用相册。它是分组，不是对象的归属。
CREATE TABLE IF NOT EXISTS households (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    name          TEXT NOT NULL,
    enabled       INTEGER NOT NULL DEFAULT 1,      -- 用于图片理解
    root_node_id  INTEGER REFERENCES household_nodes(id) ON DELETE SET NULL,
    created_at    INTEGER NOT NULL,
    updated_at    INTEGER NOT NULL
);

-- 成员：哪些对象属于哪一份图谱。一个对象可以属于多份。
CREATE TABLE IF NOT EXISTS household_members (
    household_id INTEGER NOT NULL REFERENCES households(id) ON DELETE CASCADE,
    node_id      INTEGER NOT NULL REFERENCES household_nodes(id) ON DELETE CASCADE,
    PRIMARY KEY (household_id, node_id)
);

-- Link（边）。对象之间的事实，图库级。
CREATE TABLE IF NOT EXISTS household_edges (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    kind          TEXT NOT NULL,                   -- 取值由代码目录约束（§4.6）
    from_node     INTEGER NOT NULL REFERENCES household_nodes(id) ON DELETE CASCADE,
    to_node       INTEGER NOT NULL REFERENCES household_nodes(id) ON DELETE CASCADE,
    label         TEXT,                            -- social 的标签；teacher 只存老师 → 学生
    term_override TEXT,                            -- 推导不出或推错时的兜底，例如「继母」「干妈」
    valid_from    INTEGER,                         -- 有效期，按年；空 = 不限
    valid_to      INTEGER,                         -- 半开区间 [valid_from, valid_to)
    source        TEXT NOT NULL DEFAULT 'user',    -- user | imported | suggested（§4.8）
    created_at    INTEGER NOT NULL
);

-- label 可为空，而 SQLite 把 UNIQUE 里的 NULL 当作互不相同；
-- 用表达式索引保证「同一对节点、同一种关系」只有一条边。
CREATE UNIQUE INDEX IF NOT EXISTS idx_household_edges_unique
    ON household_edges (kind, from_node, to_node, COALESCE(label, ''));

CREATE TABLE IF NOT EXISTS household_albums (
    household_id INTEGER NOT NULL REFERENCES households(id) ON DELETE CASCADE,
    album_id     INTEGER NOT NULL REFERENCES albums(id) ON DELETE CASCADE,
    PRIMARY KEY (household_id, album_id)
);
```

约束（写入时按关系目录校验，见 §4.6）：

- 对象类、关系类型、社交标签都必须在目录里；边的两端对象类必须与目录一致。
- 对称边与互逆边在写入前归一化：`spouse` 与对称的 `social` 按 id 小的在前只存一条；`teacher` 只存老师 → 学生。这样 A→B 与 B→A 不会同时存在。
- 同一个孩子最多两个 `parent`（数据允许更多，但界面提示；重组家庭可能确实有四位父母，推导时取「生父母」优先，其余用 `term_override`）。
- 不允许自己指向自己；`parent` 边成环直接拒绝（走一遍祖先检查）。
- 同一对节点、同一种关系只允许一条边。要表达「同事了两段」，合并成一个区间。
- 有效期两者都填时必须 `valid_from < valid_to`。
- 删除对象时级联删除它的锚点、成员关系与边；任何图谱的根都不能删。

**为什么值域不写进 SQL 的 `CHECK`**：按需建的表没有版本号，而 SQLite 放宽一个 `CHECK` 只能重建整张表。将来给 `social` 加一个标签、或开放 `place` 对象类，都要动表。值域写进代码目录，改一行就行，而且目录是普通数据，可以穷举测试（§7.4）。

### 4.4 关系推导

给定两个人 A、B，求「A 是 B 的 ___」。只在**拍摄当时成立**的 `parent`/`spouse` 上做**最短路径**（`social` 边不参与；来源为 `suggested` 的边也不参与，见 §4.8），把路径翻译成中文：

| 路径（相对 B） | 结果（按 A 的性别） | 备注 |
|---|---|---|
| 上 1 步 | 父亲 / 母亲 | |
| 下 1 步 | 儿子 / 女儿 | |
| 配偶 | 丈夫 / 妻子 | |
| 上 2 步（经父亲） | 爷爷 / 奶奶 | |
| 上 2 步（经母亲） | 外公 / 外婆 | |
| 下 2 步（经儿子） | 孙子 / 孙女 | |
| 下 2 步（经女儿） | 外孙 / 外孙女 | |
| 上 1 下 1（共享父母） | 有出生年：哥哥 / 弟弟 / 姐姐 / 妹妹；否则：兄弟 / 姐妹 | 需要两人出生年 |
| 上 2 下 1（父母的兄弟姐妹） | 经父亲：**伯伯 / 叔叔** / 姑姑；经母亲：舅舅 / 姨母 | 伯伯＝父之兄、叔叔＝父之弟，**需要两者的出生年**；缺年份时写「伯父或叔父」 |
| 上 2 下 2 | 堂 / 表兄弟姐妹 | |
| 配偶的父母 | 岳父 / 岳母 / 公公 / 婆婆 | |
| **下 1 步 + 配偶** | **儿媳 / 女婿** | 按孩子这一侧定：儿子的妻子是儿媳、女儿的丈夫是女婿；配偶性别与该称呼不符时退回「〈孩子〉的伴侣」或 `term_override` |
| **下 1 步 + 下 1 步 + 配偶** | 孙辈的配偶：孙媳 / 孙女婿 | 同上，按孙辈这一侧定 |
| **上 1 下 1 + 配偶** | **嫂子 / 弟媳 / 姐夫 / 妹夫** | 兄弟姐妹的配偶，按排行与性别 |
| **上 1 + 配偶** | 继父 / 继母 | 默认不推；只在 `term_override` 明确时使用 |
| 更远（亲家、堂表的下一代…） | **不写** | 4 步以上的路径容易推错，留 M2 |

推导不出的关系一律不写。卡片里少一句远比多一句错的好。**凡是靠出生年才能定的词（哥哥/弟弟、伯伯/叔叔），缺年份就退回中性写法**（兄弟姐妹、伯父或叔父），不猜。

### 4.4.1 根人物

图谱本身没有「儿子」这种词：它只有边。界面上要在人名旁边显示一个称呼，就得确定**相对谁**。这个参照点就是你提到的**根人物**——通常图谱就以此命名（「某某家」），所以它不是可选项：

- `households.root_node_id` 必填（建图时指定），界面里**置顶**并带一个「根」标记。
- 侧栏与信息面板的称呼都以根为准推导：根的父母是「父亲/母亲」，根的孩子是「儿子/女儿」，根的外祖母是「外婆」。
- 一个人可以属于多份图谱：称呼按**当前相册适用的那份图谱**的根推导，没有适用的取第一份。
- 图谱名默认填「〈根人物〉家」；相册名是磁盘目录名（改不了），两者并列显示，不强制一致。
- 换根只影响显示，不用改任何边；允许改（比如最初以孩子为根，后来改成以自己为根）。
- **根不参与提示词里的卡**：卡写的是在场两人之间的关系，根是谁都不影响。这样也不会把没在照片里露面的根人物名字发出去。

### 4.4.2 关系覆盖清单

按根人物的视角，把常见的称呼逐项对到推导规则上（这是 §4.4 的验收清单）：

| 方向 | 称呼 | 由什么推出 | 需要的数据 |
|---|---|---|---|
| 向上 | 父亲 / 母亲 | 上 1 步 | — |
| 向上 | 爷爷 / 奶奶 | 上 2 步（经父） | — |
| 向上 | 外公 / 外婆 | 上 2 步（经母） | — |
| 向上 | 舅舅 | 上 2 下 1（母之兄弟） | — |
| 向上 | 姑姑 | 上 2 下 1（父之姐妹） | — |
| 向上 | **伯伯 / 叔叔** | 上 2 下 1（父之兄弟） | **父与其兄弟的出生年**；缺则「伯父或叔父」 |
| 向下 | 儿子 / 女儿 | 下 1 步 | — |
| 向下 | **儿媳 / 女婿** | 下 1 步 + 配偶 | — |
| 向下 | 孙子 / 孙女 / 外孙 / 外孙女 | 下 2 步（分儿子/女儿） | — |
| 向下 | 孙媳 / 孙女婿 | 下 2 步 + 配偶 | — |
| 平级 | 哥哥 / 弟弟 / 姐姐 / 妹妹 | 上 1 下 1 | 两人出生年；缺则「兄弟姐妹」 |
| 平级 | 妻子 / 丈夫 | 配偶 | — |
| 平级 | 嫂子 / 弟媳 / 姐夫 / 妹夫 | 上 1 下 1 + 配偶 | 长幼 |
| 姻亲 | 岳父 / 岳母 / 公公 / 婆婆 | 配偶的父母 | — |
| 社交 | 同学 / 老师 / 学生 / 朋友 / 同事 / 邻居 | `social` 边（**不由亲属推导**） | 用户显式连一条边 |
| 兜底 | 继母 / 养父 / 干妈 / 亲家… | `term_override`，或**不写** | 用户显式填 |

**覆盖不到、且刻意不做的**：亲家（儿媳的父母）、堂表的下一代、更远的姻亲链——需要 4 步以上路径，推错比不写更糟。要做是 M2 的推导表扩展，数据模型不用改。

### 4.5 对象身份与脸名

**身份是对象的 id，不是脸名。** `household_nodes.id` 是图库里唯一的稳定身份：不随人脸重建而变，也不随改名而变。不存 `persons.id`——那张表每次重建索引都会被清空重建，只有用户起的名字靠「按脸快照 + 多数票」找回（§3 事实表）。

**脸名是锚点。** `household_node_anchors`（`kind = face_name`）把对象对应到人脸标注里的名字，**整个图库里一个脸名只对应一个对象**。因此：

- 一个对象可以有多个脸名（同一人的两个聚类、改过名前后的两个名字）。两个 `persons` 行无论同名还是不同名，都能指到同一个人。
- 一个对象可以没有脸名（没照片的祖辈）。这样的对象仍然参与推导——「外婆的母亲」这条路径要经过她——只是不会出现在任何一张卡里。
- 脸名在 `persons` 里已经不存在（被删除或被合并掉）时，锚点**保留**并在界面标「待重新关联」，不自动删：那可能是用户唯一一份亲属数据。

**对象是图库级的，图谱是分组。** 一个人在图库里只有一个对象；「我家」「爷爷奶奶家」是两组 `{根, 成员, 适用相册}`，同一个人可以同时属于两份（§4.3 的 `household_members`）。边是对象之间的事实，不属于某一份图谱。

**改名要跟着走。** 用户给人脸改名时，同步更新锚点里的旧名字（`rename_with_conn`，`t_sqlite.rs:10639` 附近，一条 `UPDATE`；表不存在则跳过）。

**自动名不算身份。** `Person 7` 这类聚类自动名不能做锚点，也不进 `{people}`（§9 的 M0）。

**重复对象**（用户手动建了一个「爷爷」，后来人脸又认出「爷爷」并导入）：第一版靠「一个脸名只对应一个对象」在导入时挡住；已经建重复的，M2 提供「合并对象」。

### 4.6 模式：代码里的封闭目录

哪些对象类、哪些关系类型、每种关系什么性质，只有**一处**定义。校验、归一化、推导、界面下拉都从它读，不散落在 SQL `CHECK` 和 `if-else` 里：

```rust
/// 对象类。第一版只开 person。
pub struct NodeClass { pub name: &'static str }

/// 一类 Link 的全部性质。
pub struct RelationType {
    pub kind: &'static str,                  // 'parent' | 'spouse' | 'social'
    pub label: Option<&'static str>,         // social 用
    pub from: &'static str,                  // 两端的对象类
    pub to: &'static str,
    pub direction: Direction,                // Directed（parent、teacher）| Symmetric
    pub inverse_label: Option<&'static str>, // teacher 的逆读作「学生」
    pub generative: bool,                    // 是否参与亲属推导
    pub time_scoped: bool,                   // 界面是否提供有效期
}

pub static NODE_CLASSES: &[NodeClass] = &[NodeClass { name: "person" }];

pub static RELATION_TYPES: &[RelationType] = &[
    // 示意：下表每行是一条 RelationType { … }，各列依次对应结构体的字段。
    // kind     label       from   to      direction  inverse  generative  time_scoped
    // parent   —           person person  Directed   —        true        false
    // spouse   —           person person  Symmetric  —        true        true
    // social   classmate   person person  Symmetric  —        false       true
    // social   teacher     person person  Directed   student  false       true
    // social   friend      person person  Symmetric  —        false       true
    // social   colleague   person person  Symmetric  —        false       true
    // social   neighbour   person person  Symmetric  —        false       true
];
```

值域不写进 SQL 的原因见 §4.3。目录是普通数据，所以「目录之外的标签被拒」「对称边归一化」「老师与学生互逆」这些规则都能穷举测试（§7.4）。

### 4.7 对象类的路线图

按对图片理解的价值排序。后面的类**现在不建**，只在这里留位置：

| 对象类 | 给描述带来什么 | 排期 |
|---|---|---|
| `person` 人 | 身份、关系、年龄 | **M1** |
| `place` 地点 | 老家、奶奶家、常去的公园、学校。把 GPS 坐标变成「有家庭含义的地名」（「在老家过的年」） | M2–M3 |
| `event` 事件 | 十岁生日、小学开学、某次旅行。让描述从「一帧」变成「一件事」 | M3 |
| `photo` 照片 | **不做节点。** 照片是证据不是实体：它断言「这些对象在某一时刻共处一处」，本身已经在 `afiles` 里 | — |

Place 与 Event 正是 §8.4 里「图谱补不上」的两块（事件、地点的家庭含义）的解法。开放一个新对象类要做三件事：在目录里登记、给它加属性列（`ensure_schema` 里按 `table_has_column` 补）、登记它与 `person` 的关系类型（出生于、居住在、参加、发生于）。宠物暂不单列，写在备注里。

### 4.8 有效期与来源：按「拍摄当时」看关系

照片都有拍摄时间，关系应当按照**拍摄当时**成立与否来写。同一条配偶边，在 2015 年的照片里还不存在，2017 年起是「妻子」，2022 年之后是「前妻」。

**有效期**（`valid_from` / `valid_to`，按年，半开区间 `[from, to)`）。设拍摄年份为 t，一条边在 t 年**成立**，当且仅当下面两条同时满足：

- `valid_from` 为空，或 `valid_from ≤ t`；
- `valid_to` 为空，或 `t < valid_to`。

由此得到几条规则：

- 推导只走**当时成立**的边。2015 年的照片不会因为两人 2017 年结婚而写出「妻子」。
- 已结束的配偶边只做一件事：在它两端直接写「前夫 / 前妻」。它不参与其它推导——前妻的父母不再是岳父母。
- 其它已结束的社交边（「曾经是同学」）不写。
- `parent` 永远不带有效期。
- 年是粗粒度：同一年内先结婚后离婚说不清，接受这个精度。

**来源**（`source`）：

| 值 | 含义 | 进不进提示词 |
|---|---|---|
| `user` | 用户在关系编辑对话框里连的 | 进 |
| `imported` | 从文件或其它模块批量导入的（如 GEDCOM 家谱文件） | 进 |
| `suggested` | 模型或启发式**建议**的，等用户确认（M2） | **不进**；确认后转为 `user` |

没有这个字段，M2 的「建议一条边」会把猜测当成事实写进描述。

## 5. 注入提示词

### 5.1 图谱卡

只包含这张照片里认出的人，只写图谱里确实存在的关系。下面是实验用的参考图谱经原型 `render_card.py` 渲染出的卡；姓名已换成化名，结构、关系词与年龄都是真实输出：

样张 A（四人公园合影，认出 4 人）：

```
人物档案（用户整理的关系图谱，可信；只用于画面里已被人脸标注认出的人。图里没有标出关系的人，不要给他编一个关系，也不要当成这个家庭的成员）：
- 李静：女；是王秀兰的女儿，是张小满的母亲，是张伟的妻子。
- 王秀兰：女；是李静的母亲。
- 张小满：男，2011 年生，拍摄时约 10 岁；是李静的儿子，是张伟的儿子。
- 张伟：男；是李静的丈夫，是张小满的父亲。
```

样张 C（两个孩子，其中一个不在图谱里）：

```
- 陈小雨：女。
- 张小满：男，2011 年生，拍摄时约 9 岁。
```

陈小雨在照片里、被识别出来了，但用户没在图谱里给她连线，所以卡片只有姓名和性别。这一行是故意留的：它测的是模型会不会自己给她编一个「妹妹」。

**规则**

- **只列在场的人**，也只写**在场两人之间**的关系。跨出画面的关系（比如在场孩子的另一位家长）不写，一是省 token，二是避免让模型联想到画面外的人。
- 社交边也写进卡：「张小满和陈小雨是同学」「张伟是刘洋的老师」。这条比「什么关系都没有」更有用——它挡住模型把同龄孩子写成妹妹。
- **关系按拍摄当时成立与否来取**（§4.8）：结婚之前不写「妻子」，离婚之后写「前妻」。
- **只有用户确认或批量导入的边才算事实**；来源为 `suggested` 的边不进卡（§4.8）。
- **没有认出任何图谱里的人 → 整卡不发**，提示词与现在逐字节一致。
- 关系词由程序算，模型不推算。
- 年龄也由程序算好写成「拍摄时约 N 岁」（用拍摄日期减出生年，不交给模型做减法）。成年人的年龄默认不写，只写出生年或不写。
- 出生地、备注默认不写；每个节点单独打开才追加。
- 推导不出的关系不写；`term_override` 生效时用它。
- 称呼（`display_name`）与人脸姓名不同时写成「称呼」，模型用称呼称呼人。
- **根人物不出现在卡里**，除非他本人在照片里：卡只陈述在场者的关系，不需要一个全局参照点。
- **人数对不上时明说。** 若这张照片检测到的人脸数多于卡里的节点数（有人没被认出，或有人的名字还没导入），卡尾追加一句「画面里还有 N 个人身份未知」。这句话是防「把名字安到别人身上」的最后一道闸——模型知道有人没有名字，就不会把 4 个名字硬分给 5 个人。

### 5.2 接进模板

- 新增一个占位符 `{family}`：展开成上面的卡，或者空字符串。占位符表从 36 个变 37 个。
- 取数点在 `prompt_context_with_conn`（`t_vl.rs:1341` 附近，现在已经在这里取标签和人名）：由文件找到相册 → 找到适用的图谱 → 认出的脸名经锚点对应到对象（取这些图谱的成员）→ 取对象之间的边，按拍摄年份筛出当时成立、且来源可信的 → 推导 → 渲染。都是一个连接上的查询，有索引。
- 11 个内置模板的共享事实块加一行 `{family}`。按 D4，这是模板的新版本。
- 共享规则里「不要推断关系」那几条要改口径：有图谱时「关系、称呼、年龄以人物档案为准，图里没有的关系不要推断」；没有图谱时保持现在的措辞。这两句随图谱是否出现切换，所以也做成占位符。
- 每次调用实际发送的提示词存在 `vl_calls.prompt_actual`，实验室里能看到那一张卡。这是有意的：出了错能查到模型当时看到了什么。

### 5.3 角色模板跟着受益

有了图谱，「爸爸的视角」不需要猜谁是爸爸。§8 的实验里模型的处理是对的：父亲在画面里就以父亲的身份写，不在画面里就写成「我在镜头后看着」。第一版不专门改角色模板；第二版可以按图谱里有没有对应关系来决定是否显示某个角色模板。

## 6. 隐私

**哪些数据会离开这台机器。** 提示词经局域网网关发往上游云端模型。今天人名已经在发（`{people}`）。图谱会新增两两关系、性别、年龄，而且它们与拍摄时间、地点出现在同一个请求里，合起来比单独一项更能识别一个人。未成年人尤其如此。

**因此：**

| 控制 | 默认 |
|---|---|
| 档案总开关「用于图片理解」 | 开；关掉后只存本地 |
| 成年人的年龄 | 不发 |
| 出生日期本身 | 永远不发，只发推算出的年龄 |
| 出生地、备注 | 不发；每个对象单独打开 |
| 发送前的知情提示 | 第一次打开「用于图片理解」时说明会发送哪些字段 |
| 预览 | 编辑器里选一张照片，逐字显示模型将看到的卡 |
| 写回 | 档案只存在图库库里，不写进照片文件、XMP 或任何导出 |

备份图库（`scripts/backup-library-db.py`）会连同档案一起备份，这是对的。

## 7. 接口、界面与改动点

### 7.1 命令（11 条，内核全在新模块 `t_household.rs`）

对象是图库级的，所以命令分成三组：读、管图谱（分组）、管对象与边。

| 命令 | 参数 | 暴露级别 |
|---|---|---|
| `get_household_overview` | — → 图谱列表、对象（含锚点与所属图谱）、边、适用相册、推导出的称呼 | 读（没有图谱表时返回 `null`，不是一个空对象） |
| `list_face_names_for_household` | — → 已命名的人脸人物（不含 `Person N`），标注哪些已导入 | 读 |
| `preview_household_card` | `fileId` → 卡文本 | 读（前缀 `preview_` 自动归为读） |
| `create_household` | `name, albumIds, rootNodeName, importNames` | 写 |
| `update_household` | `id, name, albumIds, enabled, rootNodeId` | 写 |
| `delete_household` | `id`（只删分组、成员关系与相册范围；**对象与边保留**） | 写 |
| `import_household_nodes` | `householdId, personNames` | 写（幂等） |
| `upsert_household_node` | `node`（含锚点，整批替换） | 写 |
| `delete_household_node` | `nodeId`（不能是任何图谱的根；级联锚点、成员关系、边） | 写 |
| `set_household_members` | `householdId, nodeIds` | 写（整批替换） |
| `set_household_edges` | `householdId, edges` | 写（整批替换） |

几条需要说明的约定：

- **导入是幂等的，而且不会造出第二个人。** `import_household_nodes` 对每个脸名：已经有对象锚定在这个脸名上，就只把它加进这份图谱的成员；没有才新建对象、锚点和成员关系。以后新命名了一个人再加入图谱，走的也是它。
- **`create_household` 一步建图加导入**：先按 `importNames` 导入，再用 `rootNodeName`（必须是刚导入的或已存在的脸名）设根，用户少点一步。
- **`get_household_overview` 一次返回界面要的全部内容**。侧栏和信息面板共用它，不再各自拼。
- **`set_household_edges` 整批替换与这份图谱的成员相连的全部边**（至少有一端是成员）。整批提交能在一处完成全部校验——按关系目录检查对象类、方向、标签，归一化对称边与 `teacher`，拒绝自环、成环、倒置的有效期——前端也不必维护「这条边是否已存在」。`set_household_members` 同理。

### 7.2 界面：融合进现有的人脸展示

不新开一个「家庭档案」大页面。主入口和人脸功能长在一起，用户在他本来就看的界面上看到关系：

**人物侧栏**（`Person.vue` 每一行）——名字后面加一个灰色小标签，根人物置顶并带「根」标记：

```
(头像) 张小满  根            1,204     ← 根人物
(头像) 张伟    父亲            431
(头像) 李静    母亲            428
(头像) 王秀兰  外婆             86
(头像) 陈小雨  同学             32
(头像) Person 12                （未命名，不显示关系）
```

标签相对根推导（§4.4.1）；一个人属于多份图谱时，按**当前相册适用的那份图谱**的根推导，没有适用的取第一份。推导不出就不显示。一行最多一个词，宽度不够时省略。社交关系显示为「同学 / 老师 / 朋友」等。

**右键菜单**：现有「重命名 / 删除」旁边加一项「家庭关系…」，打开关系编辑对话框；未加入图谱的人显示「加入家庭图谱」；根人物额外有「以此人为根」。

**信息面板**（`FileInfo.vue` 的人物 chip）——名字后面接关系：

```
人物   (李静) 母亲   (张小满) 儿子   (陈小雨) 同学
```

**关系编辑对话框**（新增组件，从人物侧栏打开）——只做四件事：

1. 把人设为根（`rootNodeId`）。
2. 给一个人连父母或配偶（下拉选已有节点，不手打名字）。
3. 连一条社交关系（选一个人 + 选一个标签：同学/老师/学生/朋友/同事/邻居）。
4. 显示推导出的其余关系（灰字只读），以及「导入」入口（列出还没进图谱的已命名人物）。

连边时只显示关系目录（§4.6）里登记过的选项，避免用户连出一个推不出的关系。

**有效期与来源在 M1 不露出界面**：M1 的边全部由用户手连，来源都是 `user`；表里已经留好这两列（§4.8），M2 再加起止年份的输入和「待确认建议」列表。

**设置页**：图片理解标签页里只放一个轻量卡片——总开关、适用相册、一句说明和「打开图谱」链接；不再重复成员的表格。图谱是人物的一部分，编辑入口应该在人物那里。

### 7.4 测试

- **关系推导（纯函数，最重要的一批）**：父/母、子/女、配偶、祖父母两侧、外祖父母、孙辈两侧、兄弟姐妹（有/无出生年）、伯叔姑舅姨（含「父之兄=伯伯、父之弟=叔叔，缺出生年时退化为伯父或叔父」）、堂表、配偶的父母、**儿媳/女婿**、**嫂子/弟媳/姐夫/妹夫**、孙媳/孙女婿；`social` 边不参与亲属推导；不可达 → 不写；`term_override` 生效；自环与成环被拒；相对根的称呼正确；根为空时退化为边摘要。
- **社交边**：`social` 必须有 `label`；`teacher` 反向读作「学生」；对称边归一化后只有一条；社交边进卡片但不出现在亲属推导里。
- **图谱卡渲染（纯函数）**：没有图谱 → 空；照片里没认出节点 → 空；只列在场的人；只写在场两人之间的关系；年龄由拍摄日期算出；成年人不写年龄；`share_details` 关闭时不写出生地/备注；`Person N` 不出现；多份图谱取并集。
- **模块独立性（关键回归）**：一个**没有图谱表**的图库，VL 渲染出的提示词与改动前逐字节相等；`get_household_overview` 返回 `null` 而不报错；`rename_person` 在图库没有图谱表时正常。
- **对象身份与锚点**：一个对象有多个脸名时都认得出；没有脸名的对象不进卡但参与推导；一个脸名不能对应两个对象（第二次导入被挡）；`Person N` 不能做锚点；改名同步锚点；脸名从 `persons` 消失后锚点保留。
- **导入**：只导入已命名的人；`Person N` 被排除；重复导入幂等（已存在的脸名只补成员关系）；一个人可以加入多份图谱而不产生第二个对象。
- **有效期**：按拍摄年份取边的三种情形（尚未开始 / 成立 / 已结束）；已结束的配偶写「前妻」且不再参与其它推导；已结束的社交边不写；`parent` 不带有效期；区间倒置被拒。
- **来源**：`suggested` 的边不进卡也不参与推导；确认后（转为 `user`）才进。
- **关系目录**：目录之外的 `kind` / `label` 被拒；两端对象类不符被拒；对称边与 `teacher` 归一化后只有一条；同一对节点、同一种关系只有一条边。
- **Rust 其他**：`ensure_schema` 幂等；边的整批替换与归一化。
- **前端**：`householdLogic.js` 的纯函数；侧栏标签在无图谱时不渲染；新对话框的接线约束（监听器释放、库切换重载）。
- **§8 的 6 张基准照片 + 参考图谱**作为端到端用例：卡片文本与 §5.1 的样例逐字一致。

### 7.5 上线前的验证协议

图谱卡的质量在 6 张照片、2–4 人的画面上已经验证；真正容易塌的是下面几类画面。所以先做一轮小样本人工核对，过了再谈全库。

**样本**：20–30 张，满足三条中的两条以上——人物 ≥ 4、含未成年人、同一孩子跨年份、有侧脸或背影。

**每张只核对三件事**（其余不用管）：

| 检查项 | 怎么看 | 不合格的样子 |
|---|---|---|
| 漏识别的人有没有被安错名字 | 数画面里几张脸、卡里几个人；描述里的人名是否都落在了正确的身体上 | 5 个人 4 个名字，第 5 个人被叫成了某个名字 |
| 站位有没有写反 | 对着照片看「左起」「旁边」「身后」 | 「父母一左一右」而两人都在左边 |
| 年龄有没有算错 | 拍摄年份 − 出生年 | 8 岁写成「六七岁」 |

**通过标准**：三项里前两项 0 处错误、年龄 0 处错误。出现任何一处，先修规则或修推导，不要扩量。

**记录**：每张留一条（照片、卡、描述、是否通过、错在哪），放在仓库外（不外传原图，也不把真实姓名写进仓库）。

## 8. 对照实验（2026-11-23）

### 8.1 角色列表卡（第一版方案，已弃用）

**问的问题**：给模型一张档案卡，描述会不会更像用户想要的？

**做法**：产品内置模板里取 6 个（客观描述、爸爸的视角、妈妈的视角、儿子的视角、家庭合影、亲子时光），6 张基准照片（见 `VL-提示词模板库.md` §5.2）。实验组把一张手写的档案卡插在每个模板的规则之前，跑两轮；对照组是今天同配置、不带卡的两轮。评判脚本和指标在看到结果之前写好。

实验用的卡（**姓名是化名，出生年是假设值，未经用户确认**）：

```
人物档案（用户整理的家庭关系，可信；只用于画面里已被人脸标注认出的人。
没被认出的人不要按档案里的人称呼，也不要当成这个家庭的成员）：
- 儿子：这个家庭的儿子，男，2011 年生（年龄请按拍摄时间推算）。
- 父亲：父亲，男，儿子的父亲。
- 母亲：母亲，女，儿子的母亲。
- 外婆：儿子的外祖母（外婆），母亲的母亲。
```

卡片里没有另两个孩子（样张 C 的女孩、样张 F 的另一个孩子），正好用来检验模型会不会把档案外的人说成家人。

**结果**

对照组 A、B 是今天不带卡的两轮（「提交配置终验」和「原图终验」，同一批模板与照片）；实验组带卡跑两轮。每轮 36 条。

| 指标（每轮 36 条） | 对照组 A | 对照组 B | 实验组第 1 轮 | 实验组第 2 轮 |
|---|---|---|---|---|
| 用了人名 | 7 | 12 | 28 | 26 |
| 用了人名或角色词 | 19 | 18 | 33 | 32 |
| 写明了关系（X 的母亲…） | 4 | 6 | 12 | 10 |
| 关于儿子的年龄表述，与假设的出生年一致 | 0 / 1 | 0 / 3 | 6 / 6 | 9 / 9 |
| 没有拿到可用回答（额度用尽） | 0 | 0 | 1 | 0 |
| 时段写错 | 0 | 0 | 0 | 0 |
| 把档案外的人说成家人 | 0 | 0 | 0 | 0 |
| 描述字数（中位数） | 110 | 109 | 106 | 111 |
| 输出 token（每轮合计） | 53,159 | 57,829 | 55,129 | 50,287 |
| 单次耗时（均值） | 10 秒 | 11 秒 | 26 秒 | 13 秒 |

逐条人工核对两轮的 71 条有效描述（第 1 轮 35 条、第 2 轮 36 条）：

- **人名和角色全部安对，0 处安错。** 之前反复出错的父子合影，这次「妈妈的视角」写的是「〈父亲〉戴眼镜穿深色上衣，〈孩子〉穿浅绿 T 恤」。
- **陌生人不被说成家人。** 有未具名男子的样张 E 上，两轮共 12 条都写成「男士」「一位大人」「旁边的男士」；对照组那 2 条「丈夫」没有再出现。
- **档案外的人不被说成家人。** 另两个孩子只以名字或「一位别着粉色发夹的小姑娘」「旁边几个孩子」出现。
- **没有编造档案里没有的属性**（职业、出生地都没有出现）。
- **年龄全部算对。** 2021 年的照片写「十岁」，2020 年 5 月写「9 岁」，2020 年 2 月写「八九岁」，2019 年 4 月写「七八岁」「八岁」，与假设的出生年 2011 一致。对照组同样的照片写「六七岁」（错），而且一遇年龄就绕开不写（对照组两轮只有 4 次年龄表述）。
- **角色模板的口吻对了**：父亲不在画面里时写成「我在镜头后看着你们」，没有把自己塞进画面；母亲在画面里时用「我」指自己，用「我妈」指外婆。
- **一处小的位置错误**（第 1 轮）：「父母一左一右靠近儿子」，实际两人都站在儿子左边。第 2 轮同一张写对了。

**代价与没弄清的事**

- **截断略高**：实验组两轮各有 1 次输出触到 4000 的额度（第 2 轮那次仍拿到了正文），对照组 72 次里 0 次。样本太小，不能确定是档案卡让思考变长，还是那两张照片本来就难。**产品化时要盯住这个指标**（§10）。
- **耗时不能归因**：第 1 轮均值 26 秒、第 2 轮 13 秒，对照组两轮是 10 秒和 11 秒；而每轮输出的 token 总量相当（5.0–5.5 万）。第 1 轮很可能是网关当时的负载。**没有证据表明档案卡让请求变重。**
- **实验用的是静态卡**，产品里会按照片动态生成（只列认出的人）；两者在这一步上等价，但产品里年龄由程序算好，不再让模型推算。
- **卡里的关系是我的推断**，错了模型会照着错。产品里必须让用户自己填。
- **只覆盖 6 张照片、6 个模板、2 轮**。其中只有 2 张（C、F）含档案外的人，用来测「不越界」，数量偏少。

### 8.2 图谱卡（按澄清重做）

§8.1 用的是「角色列表卡」——第一版方案，把人压平成「角色 + 属性」。你澄清要的是**关系图谱**之后，我按 §4–§5 的图谱模型重做了一遍：参考图谱只存 4 个节点、4 条边（两条 `parent` 到孩子、一条 `spouse`、一条 `parent` 到母亲），其余关系（外婆、妻子的母亲）全部由 `render_card.py` 遍历推导，然后沿用同一套模板、同样 6 张照片各跑两轮（共 72 次调用）。

图谱卡与角色列表卡的差别只在**关系是算出来的**：同一张合影，角色卡的「外婆」是手填的一个词，图谱卡的「外婆」是「李静的母亲」推导出来的。

| 指标（每轮 36 条） | 对照组（不带卡） | 角色列表卡 | 图谱卡 |
|---|---|---|---|
| 用了人名 | 7 / 12 | 28 / 26 | 25 / 23 |
| 用了人名或角色词 | 19 / 18 | 33 / 32 | 32 / 29 |
| 写明了关系 | 4 / 6 | 12 / 10 | 10 / 8 |
| 关于儿子的年龄表述正确 | 0 / 4 | 6/6、9/9 | 7/7、7/7 |
| 时段错误 | 0 | 0 | 0 |
| 截断 | 0 / 72 | 2 / 72 | 1 / 72 |
| 把图谱外的人说成家人 | 0 | 0 | 0（两张一轮共 72 条，0 处「妹妹/姐姐/表哥/堂姐/侄」等词） |
| 输出 token（每轮合计） | 53,159 / 57,829 | 55,129 / 50,287 | 38,174 / 53,163 |

**读法**：图谱卡与角色列表卡在这 6 张照片上的质量**没有可辨差异**（人名 25/36、23/36 对 28/36、26/36，落在 §5.3 说的噪声范围内）。所以选图谱的理由不是「输出更好」，而是**数据模型更强**：

- 输入更少：4 个家人只需 4 条边，不用给每个人挑一个角色词。
- 不会自相矛盾：不存在「同一个人既是表姐又是姐姐」，因为只存父母和配偶。
- 换参照点不用改数据：同一份图谱，孩子看是「外婆」，母亲看就是「我妈」。
- 加一个人自动补全他和其他人的全部关系。

**图谱卡带来的一个具体改进**（角色列表卡做不到）：样张 A 的「妈妈的视角」写成「我穿白 T 恤站在**我妈**和张伟中间」。要写出「我妈」指那位外婆，模型必须知道「外婆是李静的母亲」——这正是图谱推导出来的那条边。角色列表卡只给了「外婆」一个词，模型只能跟着叫「外婆」。

**其余核对结果**（两轮各 36 条，逐条看过；下文引文里的人名已换成化名）

- **没有一条给未连线的人编关系。** 样张 C 的另一个孩子、样张 F 的另一个孩子在图谱里都没有边，两轮 72 条描述里 0 处把她们说成妹妹、表姐、侄女。
- **样张 F 反而更谨慎**：自己写出「这更像同伴间的生日陪伴，而非明确的亲子同框」。
- **陌生人仍不被说成家人**：有未具名男子的样张 E 上，仍是「男士」「一位成年男性」「旁边那位男士」。
- **一处口吻瑕疵**（与图谱无关）：样张 E 的「妈妈的视角」把自己写成了第三人称（「他身旁的女士…」）。第一版整份实验里也出现过类似漂移。

### 8.3 两次实验共同说明的事

1. **给模型事实，比给模型形容词有用。** 两份卡都把「用了人名或角色词」从 19/36 提到 29–33/36，把年龄从 0/4 提到 15/15。
2. **「不写」也是一条能力。** 图谱外边的人、画面外的人、推导不出的关系，模型都选择了不写。卡片里那句「图里没有标出关系的人，不要给他编一个关系」是有效的。
3. **卡片的形状不影响质量，数据的结构影响可维护性。** 所以最终采用图谱。

### 8.4 从模型侧看：图谱补上什么、补不上什么

这一节是**判断**，不是实测：把「我（一个多模态模型）读这张卡时会发生什么」讲清楚，好让后面的投入落在真正有用的地方。已测的部分见 §8.1、§8.2 与 §1.4。

**图谱补上的那一层是身份与关系。** 描述家庭照片时，模型最没底的不是「图里有什么」，而是「这几个人是谁、谁和谁什么关系」。这件事模型没有内在知识，只能从长相、年龄、站位猜，而且猜得像真的——这正是改造前把 8 岁写成「六七岁」、把陌生男子写成「丈夫」的原因。名字对应到人、关系变成外部事实、年龄变成算术之后，实测安错人 0、编关系 0、年龄 14/14。

**补不上的是画面细节与事件。** 这些错误即使卡完全正确也会出现，实测里已经见到两例：

| 仍会错的地方 | 本次实测证据 | 为什么卡帮不了 |
|---|---|---|
| 空间关系（谁在谁的左/右、有没有挨着） | 卡齐全，仍写出「父母一左一右靠近儿子」，实际两人都在左边 | 站位是看图得出的，合影的对称先验会盖过画面 |
| 细节真伪（衣服纹理、手里拿的东西） | 512px 缩略图下直接写「图像内容不可见」；换原图才敢写 | 脸小、纹理糊时模型会用常识补，而不是承认看不清 |
| 口吻漂移（角色模板用错人） | 「女儿的视角」出现过母亲口吻 | 模板与人物设定之间的对齐问题，与图谱无关 |
| 事件与前后因果 | 会写「像是刚玩到一半被叫住」 | 图谱没有「拍摄前后发生了什么」 |
| 情绪与意义 | 会写「笑得开心」，也会写「舍不得」 | 表情能看，感受是模型加的 |
| **没被识别出来的在场者** | 未测 | 卡里 4 人、画面里 5 人时，模型可能把名字硬分给 5 个人，或把第 5 人当陌生人 |
| **人脸聚类认错之后** | 未测 | 卡不会纠错，只会让错的描述更笃定、更流畅 |

最后两条是最需要警惕的：**图谱不会让错误变少，它会让错误变得更有说服力。** 所以「导入的人名是否可靠」和「漏识别时怎么办」，比提示词怎么写更重要。§5.1 的「人数对不上时明说」就是为此加的。

**名字与脸的绑定方式**：模型不是「认出」了脸，而是把卡上的名字按位置和描述对上号。`{people}` 改成「按画面从左到右」之后，安错人从 4/9 降到 0/63——但这是**位置对齐，不是身份核验**。人一多（8–10 人合影）、有侧脸、背影或遮挡时，对齐会退化。要根治得给**人脸裁切图 + 名字**（§9 的 M2）。

**准确度的预期**（判断，不是实测）：家庭日常照、人脸识别无误、图谱正确、模板合理的前提下——

- 人物、关系、时间、地点、年龄：接近可信，主要剩余错误是空间站位。
- 画面内容（在做什么、有什么物件）：多数可用，家庭场景里大约七八成句子不用改。
- 氛围与意义（为什么这一刻重要）：属于写作，需要人改。

一句话：**从「经常错得离谱」变成「读起来对，偶尔有个细节要改」。**

**还没验证、必须先验的**：8 人以上的合影、侧脸与背影、漏检测、聚类认错、同一孩子跨年龄。§7.5 的验证协议就是为这几项设计的。

## 9. 分期

**M0 · 前置小修（独立可做）**

- `people_names` 过滤 `Person N`，`{people_count}` 跟着变。
- 定下内置模板的版本策略（D4）。
- 同步 `AGENTS.md:38`（迁移版本）等过期事实。

**M1 · 最小可用：一个能开关的独立模块**

- 后端：`t_household.rs`（`ensure_schema` 按需建六张表、11 条命令、关系目录、关系推导、按拍摄时间取有效边、图谱卡渲染）、`{family}` 占位符、`people_names` 过滤 `Person N`。
- **身份、有效期、来源三样 M1 就落进表里**（§4.5、§4.8）：对象有稳定 id、脸名是锚点、边带 `valid_from` / `valid_to` / `source`。按需建的表没有版本号，后补列要写加列逻辑，所以现在就留。
- 建图的主路径就是你说的那条：**从人脸标注导入人名**（`list_face_names_for_household` → 勾选 → `create_household(name, albumIds, rootNodeName, importNames)`），用户再连**父母、配偶、社交**三种边；根人物必填。
- 前端融合展示：人物侧栏名字后的称呼标签、右键「家庭关系…」、信息面板人物 chip 上的关系词；设置页只放开关、相册范围与一个链接。
- 独立性回归测试：没有图谱表的图库，提示词逐字节不变、概览返回 `null`、改名照常。
- 一次基准评估（§8 的 6 张照片）。
- 不做图形树（M2）。

**M2 · 让图谱更好用，也让描述更准**

按「投入换准确度」排序：

1. **人脸裁切图 + 名字**（准确度收益最大的一项）。整张照片之外，把每个已识别的人脸的裁切小图连同名字一起发。现在的名字是**靠位置对齐**绑到脸上的（§8.4），人一多、有侧脸或遮挡就会退化；裁切图让绑定变成明确的。代价是请求多出几张图、几倍 token，所以做成可按模板或按运行开启。
2. **结构化输出**：模板可以声明分字段返回（谁 / 在哪 / 在做什么 / 光线 / 不确定项），而不是一段散文。写散文时模型会为了通顺补上没看见的东西；分字段时「不确定」有地方放。
3. **图形化家庭树视图**（拖拽连线），数据模型不变。
4. 从名字和合影次数**建议**一条边，用户确认后才生效（名字里带「外婆」、和孩子的合影最多的大人…）。
5. 推导表补全到多代与姻亲（目前到「配偶的父母」为止）。
6. 角色模板按图谱裁剪：图谱里没有对应关系就不显示「女儿的视角」。
7. 预览里的「试一次」按钮；成年人可选年龄段。
8. **有效期的界面**（连边时可选填起止年份）与**待确认建议**列表（`suggested` 的边逐条确认或丢弃）。
9. **合并对象**：同一个真人被建成两个对象时并成一个，锚点、成员关系、边都跟过去。

**M3 · 探索**

- **同事件的多张照片一起描述**（单张只能写「一帧」，多张才写得出「事件」）。这是 F3 多图能力的延伸，需要网关支持一条消息多图（2026-11-11 实测已支持两图）。
- **Place 与 Event 两类对象**（§4.7）：老家、奶奶家这类有家庭含义的地名，和十岁生日、开学、旅行这类事件；连上「出生于 / 居住在 / 参加 / 发生于」四种关系。这是补上「事件」与「地点含义」的办法。
- 用图片理解给相册**建议**分类（家庭/工作），帮用户定适用范围。
- 人物外观小传：从人脸封面生成「戴眼镜、短发」之类的辨认线索（默认关闭）。
- 家庭词典：老家的说法、节日、宠物的名字。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 图谱填错，描述跟着错得很自信 | 预览逐字可见；每张标注都存了当时的提示词，可追溯。**卡不会让错误变少，只会让错误更流畅**（§8.4），所以导入的人名是否可靠比措辞重要 |
| 漏识别的人被安上别人的名字 | 卡尾「画面里还有 N 个人身份未知」（§5.1）；§7.5 的第一项检查专测这个 |
| 人脸裁切图带来的额外隐私面 | 裁切图仍然是这个人，但更清晰。默认关闭，只在用户为某个模板打开时发送，并在开关旁写明 |
| 同一个真人被建成两个对象（手建一个，又导入了一个脸名） | 一个脸名只能对应一个对象，导入时挡住；已经重复的用 M2 的「合并对象」（§4.5） |
| 关系变了但没填有效期（离婚、毕业） | 有效期是可选的，不填就当一直成立，界面上给出提示；卡片按拍摄年份取边，填了就自动正确（§4.8） |
| 模型建议的边被当成事实 | `source = suggested` 的边不进卡、不参与推导，确认后才转为 `user`（§4.8） |
| 推导出的关系词错了（如把「继母」推成「母亲」） | 推导只覆盖确定的路径；不确定就用 `term_override`；推导结果在界面上灰字显示，用户能看见 |
| 没被认出来的家人被当成陌生人 | 这是更安全的一侧错误。规则写的是「身份不确定」，不是「不是家人」 |
| 未成年人信息离开设备 | 年龄只发推算值；总开关；知情提示；成年人默认不发 |
| 模型过度使用图谱，把只认出一人的照片也写成「一家人」 | 卡片只列在场的人；评估里把「图谱外的人被说成家人」作为硬指标（§8.2 已测） |

## 11. 需要你定的事

1. **表要不要按需创建？** 我建议**按需**（§4.3）：不建图谱的图库连表都没有，模块删掉就等于没这功能。代价是表结构没有版本号。若你更看重与仓库现有迁移约定一致，就改成迁移 v33，其它设计不变。
