# F5 · 人脸归属（把脸归到已有名字的人物下）技术方案

> 状态：**已定稿**（2026-11-24，你回复「都按建议」，决定见 §13）· 分支 `develop` · 按 §10 的分期实施。
> 数字与锚点核对于提交 `0f9805b5`；以代码为准，对不上就改本文。
> 与 F4 的关系：F4（人物关系档案）用脸名做锚点；本方案让「一个名字一行人物，重建索引后也不散」成立。两边互不阻塞（§5.6）。

## 0. 一页结论

**要做的事**：在人物面板里把若干人物行「关联到已有名字」，并让这个决定在每次重建人脸索引之后仍然成立。

| 场景 | 现在 | 做完之后 |
|---|---|---|
| 同一个人分成好几行 | 只能把它们改成同一个名字，面板上还是几行 | 并成一行，脸数相加 |
| 重建索引之后 | 同名的几个簇各自成行 | 同名的脸仍在同一行 |
| 聚类把两位已命名的人混进一个簇 | 票少的那一位被悄悄改名 | 各自保留自己的名字 |
| 重建索引中途取消或出错 | 已输入的名字可能丢 | 库保持原样 |
| 关联错了 | — | 可以撤销 |

**九个决策**（理由见对应章节）：

| # | 决策 | 为什么 |
|---|---|---|
| D1 | **名字是用户的断言，按脸记住**；聚类只负责给还没有名字的脸分组 | 现在名字记在「簇」上，靠多数票找回：并进去的脸一重建就散，少数派会被改名（§5.1） |
| D2 | **一个名字一行人物** | 提示词和搜索本来就按名字取人，两行同名对它们来说就是同一个人（§5.1） |
| D3 | **重建时先聚类、后在一个事务里换人** | 聚类只读库，可以挪到清空之前；取消或出错时库还是原样（§5.2） |
| D4 | **合并是物理的**：把脸移过去、删掉空行 | 只在界面上归组的话，「人物行」和「人」还是两回事，每处用到人物的地方都要各自聚合（§5.3） |
| D5 | **目标必须已经有名字**；「先并再取名」是先给其中一行命名，再把其余并进去 | 没有名字的决定，重建后无处可记 |
| D6 | **可以撤销**：合并命令返回被移动的脸，记录存进每库状态；撤销就是把这些脸拆成一个新人物 | 合并错了，描述和搜索会跟着错。Immich 的合并不能撤销，2024 年就有人提了拆分诉求（§5.4） |
| D7 | **第一阶段不改表**；隐藏人脸放到第二阶段（迁移 v33） | 名字按脸记之后，「单张脸改派在重建后保持」不再需要新列（§5.7） |
| D8 | **不做自动建议** | 实测：默认阈值下没有一张未命名的脸会和已命名的人聚到一起；按相似度也找不到碎片（§2） |
| D9 | 新代码放新文件 `t_person_assign.rs`；对上游代码的改动只限 §7 的适配点，每条有测试 | 仓库红线 7 与「不加厚巨石文件」 |

**明确不做**（至少第一阶段）：改聚类算法或阈值；隐藏或忽略人脸；在照片上手动框人脸；改 `persons` 表结构；图形化界面。

## 1. 问题

### 1.1 现在能做什么

人物面板（`Person.vue`）每一行是一个聚类。对一行只能做两件事：改名、删除。

- **改名**（`rename_with_conn`，`t_sqlite.rs:10639`）只是把这一行的名字换掉。要把同一个人的两行并起来，只能把它们改成同一个名字，行数不变。
- **删除**（`delete_with_conn`，`t_sqlite.rs:10666`）把脸与人物解绑、删行。脸还在，下次重建索引会重新聚成一个 `Person N`。

没有「把这一行归到已有名字下」。

### 1.2 你的库里的样子

2026-11-23 的只读快照，只取计数：

| | 行数 | 脸数 |
|---|---|---|
| 你命过名的 | 10 | 1207 |
| 未命名（`Person N`），3 张脸以上 | 87 | 448 |
| 未命名，只有 1–2 张脸 | 461 | 677 |
| 合计 | 558 | 2332 |

已命名的 10 行每个名字一行。所以「一个人有多条」在你的库里是两种情况：某位没命过名的人被切成了几个 `Person N`；或者某个已命名的人另有未命名的碎片。

### 1.3 碎片从哪来

聚类只有阈值一个可调参数（`configStore.js:270`，四档 0.35 / 0.45 / 0.55 / 0.65，是余弦距离，越小越严，默认 0.55）。同一个阈值下，有的人是完整的，有的人被切开。

所以要么让用户手动归并，要么换算法。本方案做前者。

## 2. 为什么不能靠调阈值（实测）

**做法**：按 `t_cluster.rs` 的规则用 Python 重写一遍聚类（余弦距离、`dist < threshold` 连边、权重 `(1 − dist)²`、每张脸保留 80 条边、同一张照片里的脸不连边、按脸 id 顺序做 Chinese Whispers、最多 20 轮），在快照的 2332 张脸上按四档阈值各聚一次。

**模拟是可信的**：默认阈值 0.55 下，它和库里存的划分逐脸一致（调整兰德指数 1.0000，同样 558 个簇）。

| 阈值 | 聚类数 | 已命名的 10 个人 | 混了两位已命名人物的簇 | 未命名的脸自动获得名字 |
|---|---|---|---|---|
| 0.35 最严 | 1002 | 只有 1 个完整；878 张脸的那位被切成 160 块 | 0 | 0 张 |
| 0.45 | 721 | 2 个完整；同一位被切成 46 块 | 0 | 0 张 |
| **0.55 默认** | **558** | **10 个都完整** | **0** | **0 张** |
| 0.65 最松 | 290 | 9 个完整 | **1 个：两位已命名的人物和 436 张未命名的脸并成一簇，共 489 张脸** | 83 张（来自 55 个小聚类） |

「自动获得名字」指未命名的脸落进某个已命名人物占多数的簇，按现在的多数票规则会被起名。

两点结论：

1. **默认和更严的三档，没有一张未命名的脸会和已命名的人物聚到一起。** 放宽到最松能归位 83 张，代价是把两位已命名的人并到一起：按现在的多数票，其中一位的 11 张脸会被改成另一位的名字。
2. **按相似度找碎片也不行。** 548 个未命名聚类里，没有一个落在任何已命名人物自己的范围内（脸到本人质心的相似度，够不上本人最外侧 10% 的脸）。所以 D8：不做自动建议。

有一个数字说明收益有多大：231 个未命名聚类、533 张脸处在中间地带——比任何别的已命名人物都更接近某个人，但不在那个人的范围内。它们可能是同一个人在难认的条件下拍到的，也可能是长得像的亲属，数据分不出来，要你来看。如果其中一部分确实是碎片，并进去之后有名字的脸会明显增加（现在 1207 张）。

模拟脚本在临时目录里，会丢；规则已全部写在上面，可以照着重做。

## 5. 设计

### 5.1 名字按脸记（D1、D2）

一句话：**一张脸只要有过名字，重建之后还叫这个名字。**

今天的规则是「一个簇一个名字，票多者得」。改成三条：

1. 有名字的脸，回到自己名字的人物行。**同一个名字只建一行。**
2. 没有名字的脸，跟着自己所在的簇：
   - 簇里只出现一个名字：跟着这个名字。新照片里像他的人就这样自动归过去，和今天一样。
   - 簇里没有名字：新建一个 `Person N`，和今天一样。
   - 簇里出现两个以上的名字（算法把两位已命名的人混在了一起）：新建一个 `Person N`，等用户处理，不按多数票硬分。
3. `Person N` 的编号规则不变，按簇的顺序。

**没有同名簇、没有混簇的时候，结果和现在逐脸相同。** 这是回归保证，写成测试（§8 的 T-R3）。

### 5.2 重建流程：先聚类，后换人（D3）

```rust
pub fn cluster_faces<F, C>(threshold: f32, progress_fn: F, is_cancelled_fn: C)
    -> Result<usize, String>
{
    // 1. 只读：记下每张脸现在的名字，读出全部脸。库不动。
    let named_faces = Face::get_named_person_snapshot()?;
    let slim_faces = Face::get_all_for_clustering()?;            // 加 ORDER BY id

    // 2. 纯计算：建图、迭代，直到分出簇。不碰数据库，随时可以取消。
    let clusters = match compute_clusters(&slim_faces, threshold, progress_fn, is_cancelled_fn)? {
        Some(clusters) => clusters,
        None => return Ok(0),                                     // 取消：库还是原样
    };

    // 3. 一个事务：清空人物，按 §5.1 重新落库。
    let mut conn = open_conn()?;
    let assigned = restore_persons_with_conn(&mut conn, &slim_faces, &clusters, &named_faces)?;
    drop(conn);

    // 4. 缩略图（不变）
    Person::update_all_thumbnails()?;
    Ok(assigned)
}
```

- `compute_clusters`：现在 `t_cluster.rs` 第 3–7 步原样搬出，不碰库。
- `restore_persons_with_conn`：新函数。事务里先调已有的 `reset_all_assignments_with_conn`，再按 §5.1 落库。需要新增 `Person::create_with_conn`。

三个后果：

- 取消或出错时库不变。今天会留下清空的、或者只建了一半的 `persons`。
- 数千条语句从「各自自动提交」变成一个事务。重建的收尾预计更快，没有测量。
- **索引进行中不许合并**（§5.3 第 6 条）。否则合并会被聚类开始时拍的快照盖掉。

### 5.3 合并命令 `merge_persons`

```
merge_persons(personIds: number[], targetPersonId: number)
  → { targetPersonId, mergedPersonIds: number[], movedFaceIds: number[] }
```

| # | 规则 | 理由 |
|---|---|---|
| 1 | 目标必须存在，并且有用户起的名字（不是 `Person N`，不为空）。否则报「目标人物还没有名字」 | D5 |
| 2 | 来源必须存在、不能含目标；重复的 id 去掉 | — |
| 3 | 一个事务里：来源的脸全部改指到目标（逐张走已有的 `assign_to_person_with_conn`，搜索索引同步更新），然后删掉来源行 | D4；搜索和提示词立刻生效 |
| 4 | 其它名字与目标相同的行也一并并入 | D2 |
| 5 | 目标的封面和缩略图不动 | — |
| 6 | 人脸索引进行中拒绝 | §5.2 |
| 7 | 返回被移动的脸 | 撤销要用 |

「先并再取名」（几个未命名的人其实是同一个人）：前端先给第一行改名，再把其余行并进去。两步不原子，中间失败只会留下一行已经改过的名字，没有损失。

### 5.4 撤销（D6）

- **记录**：`{ targetId, targetName, faceIds, at }`，存进每库状态的 `personMerges`，最多 20 条，新的在前。要给 `LibraryState` 加一个字段（`t_config.rs:410–436`）：它是强类型的，前端多传的字段会被丢掉。
- **撤销命令**：`move_faces_to_new_person(faceIds) → newPersonId`。把这些脸移进一个新建的、没有名字的人物行（`name = NULL`，面板显示「未命名人物」），再用已有的 `Person::update_thumbnail`（`t_sqlite.rs:10577`，现在没有调用方）给它生成缩略图。已经不存在的脸跳过；一个都不剩就报错。
- **撤销之后的下一次重建**：这些脸没有名字，跟着簇走，回到合并之前的样子。
- **局限**：如果合并之后、撤销之前重建过一次索引，碎片那一簇里新加进来的、跟着得了名字的脸不会一起拆出去。撤销只动记录里的那些脸。

### 5.5 目标列表 `list_person_targets`

返回所有「有用户起的名字」的人物（id、名字、脸数、缩略图），给选择对话框用。判定与 §4 那条 SQL 相同，按名字排序。只读命令。

### 5.6 与 F4 的衔接

- F4 按脸名锚定对象，不依赖人物行。本方案之后一个名字只有一行人物，脸名与人一一对应，从人脸标注导入时更干净。
- F4 的 M0 过滤 `Person N` 时，要把 `name IS NULL` 也算作未命名（撤销会造出这样的行）。VL 的 `people_names` 与搜索的 `people_of` 本来就跳过空名字（`t_vl.rs:1467`、`t_fts.rs:559–560`）。
- F4 §4.5 已经写明「把人脸改成已有名字时锚点怎么办」。`merge_persons` 不改名字，不涉及锚点。

### 5.7 第二阶段：照片里改、隐藏

- **照片里改**：信息面板的人物标签上加菜单「这不是 X，是…」或「这是谁？…」，弹出同一个选择对话框，调 `assign_faces_to_person(faceIds, targetPersonId)`。标签对应那张照片里该人物的脸，`getFacesForFile` 已经给出 face id，不用在照片上画框。名字按脸记之后，这样改过的脸重建后保持，**不需要改表**。
- **隐藏**：给 `faces` 加一列 `hidden`（迁移 v33）。人物面板、信息面板、VL 取名、缩略图都跳过隐藏的脸。需要新列，因为 `persons` 每次重建，挂在人物行上的标记留不住。
- **折叠小聚类**：面板里「隐藏只有 1–2 张脸的未命名人物」。分页在服务端，要给 `get_persons_page` 加一个可选的过滤条件。默认关。

## 6. 界面

### 6.1 人物面板（`Person.vue`）

贴着现有结构加，不重排：

- **行菜单**多一项「关联到已有名字…」，放在改名和删除之间。
- **多选**：按住 Ctrl / ⌘ 点行是勾选，普通点击还是「选中并浏览」。勾选后列表上方出现一条操作条：「已选 N 个人物 · 关联到已有名字 · 取消」。选择状态跨分页保留（记 id）。
- **撤销**：合并成功后，列表顶部出现「已把 2 个人物关联到「小明」 · 撤销」，10 秒后消失。面板菜单里加「撤销上次关联」，有记录就可用，跨会话保留。
- **合并之后**：当前选中的行被并掉了，就改为选中目标行；列表重新加载。

### 6.2 选择对话框（新文件 `PersonMergeDialog.vue`）

- 外壳用现成的 `ModalDialog.vue`。内容是一个搜索框加一组圆形头像（缩略图、名字、脸数）。

- 选中后确认：「把 2 个人物（共 81 张脸）关联到「小明」？可以在人物面板菜单里撤销。」
- 纯逻辑抽到 `src/common/personMerge.js`：过滤与排序、确认文案的参数、撤销记录的增删与上限、§6.3 的两处改写。按仓库惯例只测这一层。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 合并错了，描述和搜索跟着错 | 确认框写明张数；可以撤销，跨会话；对话框只列有名字的人物，并显示各自的脸数 |
| 撤销记录里的脸已经不存在（重置索引、文件被删） | 撤销时跳过；一个不剩就报错，不做半截操作 |
| 「同名即同一人」把两位真同名的人并在一起 | 这是提示词和搜索今天已有的口径。名字要能区分；对话框里能看到每个名字的脸数 |
| 改名成已有的名字，仍然会出现同名两行 | 今天的做法就是这样。下次重建会并成一行，也可以用「关联到已有名字」立刻并掉 |
| 用户把人名起成 `Person` 开头 | 现有判定会把它当成自动名。第一阶段沿用同一条判定，不扩大问题 |
| 改的是上游的聚类收尾逻辑 | 只动 A1–A3；算法部分原样搬移；T-R3 钉住「没有同名簇与混簇时结果不变」 |
| 与上游同步冲突 | 上游 v0.4.1 待同步的提交没碰 `t_cluster.rs`、`Person.vue`；`main.rs`、`t_sqlite.rs` 有重叠，都是几行 |
| 浏览器（连 lapd）里用不了 | 3 条命令默认都在桥接白名单里，写入级别，普通令牌可用；验证时在浏览器里走一遍 |
